# Rebuilt from scratch on 2026-08-13 after the previous requirements.txt
# (kept as requirements.txt.bak_inconsistent) turned out to be internally
# inconsistent -- most importantly torch==2.4.1 paired with mmcv==2.1.0,
# a combination with no matching prebuilt wheel anywhere (mmcv 2.1.0's CPU
# wheels top out at torch 2.1.0; mmsegmentation/mmdet themselves declare
# mmcv<2.2.0, and the only mmcv build with a torch-2.4 wheel is 2.2.0) --
# and pinned to numpy==2.0.2, which breaks torch's numpy-1.x-ABI compiled
# extensions. That combination could never have been installed together via
# wheels; this file is a real `pip freeze` of a venv that was built version
# by version, verified at each step against real workloads (see below), not
# a merge of old, possibly-stale pins. Also dropped a large amount of
# scRNA-seq/bioinformatics cruft (rpy2, scvi, anndata2ri, leidenalg, igraph,
# hyperopt, Pyro4, opendatalab, openxlab, aliyun-*, ...) that had nothing to
# do with any script in this Organotchi tree -- apparently
# carried over from a much broader environment.
#
# Requires Python 3.10 specifically (not whatever `python3`/`python3 -m venv`
# defaults to) -- torch==2.1.0/mmcv==2.1.0 have no prebuilt wheels for
# Python 3.12+, and this project's own custom mmseg dataset (MS2D, see
# below) was never tested under anything newer.
#
# Install with --no-deps: this file is already a full `pip freeze` (a
# complete, verified transitive closure), and installing it WITHOUT
# --no-deps lets pip's resolver additionally pull in plain "opencv-python"
# (the GUI build, needing libxcb/libGL, and requiring numpy>=2) to satisfy
# mmcv/mmengine's own unpinned "opencv-python>=3" declared dependency --
# reintroducing the exact numpy<2-vs-opencv conflict this file's own
# opencv-python-headless pin exists to avoid (confirmed directly: a plain
# `pip install -r requirements.txt` pulls in opencv-python 4.11+ on top of
# the headless build listed below; `--no-deps` does not):
#   python3.10 -m venv venv
#   venv/bin/pip install --no-deps -r requirements.txt
#
# Verified against real workloads in this venv, not just import checks:
#   - mmsegmentation training: a real 2-iteration run of
#     mmsegmentation/tools/train.py against
#     configs/segformer/Organoid-Segmentation-lancaster/split-0.py on real
#     Lancaster training data -- dataset loading, model construction,
#     backward pass, and checkpoint save all completed successfully.
#   - OrgLine (detector + SAM2 mask prediction): a real end-to-end run of
#     benchmarking/adapters/predict_orgline.py against one real Intestine
#     ground-truth image -- 62 instances detected and saved, using the SAME
#     torch==2.1.0 as mmsegmentation above (OrgLine's own frozen env, not
#     reproduced here, had used torch==2.13.0/numpy==2.5.1 -- installed
#     unpinned per benchmarking/environments/README.md's own recipe, not a
#     genuine hard requirement; it runs fine on the older, mmcv-compatible
#     torch pinned here, so one shared venv covers both without needing
#     OrgLine's separate orgline_venv/ going forward).
#   - Every data_analysis/, manuscript/, and non-tool-specific benchmarking/
#     script compiles and its heaviest modules (utils_plot.py via
#     case_study_pipeline.import_utils_plot, utils_segmentation.py,
#     utils_morphology.py, case_study_pipeline.py) import cleanly.
#
# Two real per-tool venvs remain genuinely separate on purpose -- their pins
# are flatly incompatible with numpy<2/torch==2.1.0 above, not just
# untested: Cellpose/StarDist/GOAT (benchmarking/environments/*_venv/,
# numpy==2.5.1/torch==2.13.0/opencv-python-headless==5.0.0.93) and MOrgAna
# (conda env, Python<3.10 required). See
# benchmarking/environments/README.md.
#
# mmcv==2.1.0 has NO prebuilt wheel on PyPI (only a source tarball) -- a
# plain `pip install -r requirements.txt` without the --find-links line
# below would silently try to compile it from source (needs a C++ toolchain,
# slow, and may not match torch's ABI). The prebuilt CPU wheel for this
# exact torch version lives on OpenMMLab's own index instead, added below.
#
# A local environment quirk, unrelated to package versions: this machine's
# python3.10 is a Guix-provided build whose linker doesn't search this
# Ubuntu system's standard library paths, which breaks pip-installed binary
# wheels (numpy, opencv, ...) needing libz.so.1 at runtime. venv/bin/activate
# has been patched with a small, narrowly-scoped LD_LIBRARY_PATH fix for
# this (see the comment there) -- plain `source venv/bin/activate` is enough,
# no manual environment setup needed.
#
# opencv-python-headless (not opencv-python) is deliberate: the GUI build
# pulls in libxcb/libGL and other display dependencies this headless,
# CPU-only pipeline never needs, and its newer releases require numpy>=2,
# conflicting with torch's numpy<2 requirement. mmcv/mmengine list plain
# "opencv-python" as a dependency and `pip check` will always flag it as
# "missing" as a result -- harmless, both packages provide the same `cv2`
# module and installing the GUI build instead would only reintroduce the
# libxcb dependency for no benefit.
#
# mmsegmentation and OrgLine are NOT in this pinned list -- both are
# installed editable from local vendored source, not PyPI/git:
#   pip install --no-deps -e mmsegmentation
#     (this project's own fork -- custom MS2D dataset class, custom
#     configs/_base_ files; the plain PyPI mmsegmentation==1.2.2 package
#     does NOT have these and training will fail with
#     "MS2D is not in the mmseg::dataset registry" without this)
#   cd benchmarking/environments/OrgLine && pip install --no-deps -e .
#     (see benchmarking/environments/README.md's OrgLine section for the
#     checkpoint download steps this also needs)
